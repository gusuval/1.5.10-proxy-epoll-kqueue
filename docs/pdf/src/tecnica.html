Visión general

El proyecto es un proxy inverso de capa 7 escrito en C11 sin frameworks, directamente sobre las APIs del sistema operativo. Recibe conexiones HTTP y HTTPS en uno o varios puertos, decide el destino por el nombre de dominio (Host:) y reparte las peticiones entre varios servidores backend.

Arquitectura

Procesos

El master no atiende tráfico. Valida la configuración, crea los workers con fork(), les envía la config por un socketpair, vigila el fichero, atiende las señales, relanza workers caídos y sirve las estadísticas. Cada worker ejecuta un event loop de un solo hilo y dos hilos auxiliares (sondas de salud y escritura del log) que nunca tocan las conexiones.

Flujo de una petición

  1. El kernel entrega la conexión a un worker (SO_REUSEPORT en Linux).
  2. Si el frontend es TLS, se completa el handshake y se elige el certificado por SNI.
  3. Se parsea la cabecera en cuanto está completa y se busca la ruta por Host:: exacta → wildcard → default.
  4. La estrategia del backend elige un servidor sano. Se reutiliza una conexión del pool keep-alive o se abre una nueva.
  5. Se reenvía la cabecera reescrita (X-Forwarded-*, sin hop-by-hop) y el cuerpo en streaming.
  6. La respuesta vuelve reescrita (sin X-Backend-Load). Al terminar, la conexión al backend vuelve al pool y la del cliente espera la siguiente petición.

Cada objeto registrado embebe un io_handler_t con su callback. io_event_epoll.c y io_event_kqueue.c implementan solo add/mod/del y la espera; los timers y los callbacks diferidos son comunes (io_event_common.c).

Edge-triggered y sess_drive

Todos los fds se registran una sola vez, con lectura y escritura, en modo edge-triggered (EPOLLET / EV_CLEAR). El kernel avisa una vez por cambio de estado, así que cada sesión lleva dos flags por fd: rd y wr ("el último intento no terminó en EAGAIN").

sess_drive(s):
  repetir (máx. 32 vueltas):
    cli_read      /* socket cliente → in (hasta EAGAIN o buffer lleno) */
    process       /* parsear, enrutar, mover cuerpo in → uo           */
    up_io         /* connect, uo → backend, backend → ui               */
    process       /* respuesta ui → out                                */
    cli_write     /* out → socket cliente                              */
  mientras haya progreso
  si se agota el presupuesto: io_loop_defer(redrive)

Como se repite hasta que no hay progreso, nunca queda trabajo pendiente sin un evento que lo despierte, el error clásico con edge-triggered. El presupuesto de 32 vueltas evita que una transferencia grande acapare el loop.

Timers y reloj

Los timers viven en un min-heap. io_timer_set es perezoso: retrasar un deadline solo actualiza un campo, y el timer se reubica cuando vence su clave antigua; adelantarlo sí reordena el heap. Así, refrescar un timeout con cada byte recibido cuesta O(1).

Bug corregido. io_loop_now() es un reloj cacheado por iteración. En la primera versión se actualizaba después de despachar los eventos, así que tras un periodo ocioso los handlers calculaban deadlines ya vencidos (408/504 espurios). Ahora se actualiza justo después de epoll_wait/kevent, con un test de regresión (test_now_fresh_in_handler).

Liberación diferida

Un mismo lote de epoll_wait puede traer varios eventos de un objeto que se cierra al procesar el primero. Liberarlo en ese momento sería un use-after-free. Por eso close marca el objeto como cerrado (los eventos tardíos se ignoran) y el free se encola con io_loop_defer, que se ejecuta al final de la iteración en orden FIFO.

Master y workers

Canal master → worker

Cada worker recibe su configuración por un socketpair. El mensaje lleva una cabecera fija y, en BSD, descriptores adjuntos (SCM_RIGHTS):

{ magic = 0x50525859, cmd = CHAN_CONFIG, len, nfds }
payload: base_dir '\0' texto_toml '\0' claves_de_listener separadas por '\n'

El master envía el texto ya validado en lugar de pedir a cada worker que relea el fichero. Así todos aplican exactamente la misma versión aunque el fichero cambie mientras tanto. Si el canal se cierra (murió el master), el worker inicia una parada ordenada: no quedan procesos huérfanos.

Sockets de escucha

PlataformaEstrategiaMotivo

macOS/BSDEl master abre los sockets y los envía a los workers por el canalAllí SO_REUSEPORT no reparte carga

En una recarga, cada worker sincroniza sus listeners con los frontends nuevos: conserva los existentes, abre los añadidos y cierra los eliminados.

Señales, relanzamiento y parada

Todas las señales se procesan con el self-pipe trick: el handler solo escribe un byte en una tubería registrada en el loop.

Buffers y contrapresión

Los buffers salen de un pool mmap por worker y se piden solo cuando hacen falta: una conexión keep-alive ociosa no retiene ninguno. La contrapresión sale sola. Si out se llena porque el cliente lee despacio, process deja de vaciar ui, se deja de leer del backend y la ventana TCP frena al servidor. Con 10 MB de subida, el pico de memoria medido por worker fue de 13 MB.

HTTP/1.1

Parser

La cabecera se busca como \r\n\r\n, recordando hasta dónde se ha escaneado, y se parsea de una vez cuando está completa. Los campos son punteros al buffer, sin copias. Así se tolera cualquier fragmentación (hay tests que alimentan el parser byte a byte y en trozos aleatorios) sin reescanear. Validaciones:

  • Método como token, versión exactamente HTTP/1.0 o HTTP/1.1, un único espacio entre elementos.
  • Nombres de cabecera como token, sin espacio antes de :. Se rechazan el obs-fold y los caracteres de control.
  • Host obligatorio en 1.1 y único; se le quita el puerto.
  • Anti request smuggling: Content-Length + Transfer-Encoding → 400; varios CL distintos → 400; TE sin chunked final → 400.
  • Cabecera de más de 16 KB → 431.

Cuerpos

http_body_t solo sigue los límites del mensaje. Los bytes se reenvían tal cual, sin decodificar ni almacenar.

Keep-alive, pool y reintento

  • Cliente: persistente por defecto en 1.1; en 1.0 solo con Connection: keep-alive.
  • Backend: pool LIFO de conexiones ociosas por servidor (max_idle, upstream_idle). Una conexión vuelve al pool si la respuesta terminó limpia, el backend no pidió cerrar y no sobran bytes. Mientras está en el pool, cualquier dato o cierre la invalida (se confirma con MSG_PEEK para descartar eventos tardíos).
  • Reintento único: si una conexión reutilizada falla antes del primer byte de respuesta y la petición es idempotente y sin cuerpo, se reenvía por una conexión nueva. Para eso se conserva la cabecera ya enviada en uo. Un POST nunca se reintenta.
  • Si el connect falla, se prueba con otro servidor (hasta 3 intentos, excluyendo los ya probados).

Pipelining y WebSocket

Las peticiones pipelined se leen por adelantado hasta llenar in, pero se despachan en serie: la siguiente empieza cuando la respuesta anterior se ha leído entera del backend. Así el orden queda garantizado sin colas, y cada petición puede ir a un backend distinto.

Si la petición trae Connection: Upgrade y el backend responde 101, la sesión pasa a TUNNEL: copia bytes en ambos sentidos hasta que un lado cierra. La conexión nunca vuelve al pool.

TLS y SNI

Cada certificado de un frontend tiene su SSL_CTX (TLS ≥ 1.2, sin compresión ni renegociación, escrituras parciales). El SSL nace con el contexto del default_cert, y el callback de servername lo cambia con SSL_set_SSL_CTX según este orden:

  1. Coincidencia exacta con el patrón sni de la config.
  2. Wildcard de una sola etiqueta (RFC 6125): *.example.com cubre a.example.com, no a.b.example.com. Gana el patrón más largo.
  3. Si no hay coincidencia, default_cert.

Tras el handshake, la sesión copia el nombre SNI y el patrón servido. Si el cliente envió SNI, el Host es distinto y el patrón no lo cubre → 421 Misdirected Request. El handshake no bloquea: SSL_ERROR_WANT_READ/WRITE se traducen a los flags rd/wr, incluidos los casos cruzados (una lectura que necesita escribir, y al revés).

Enrutamiento, balanceo y salud

Enrutamiento

Cada frontend tiene su tabla: hash djb2 con direccionamiento abierto para dominios exactos, lista de wildcards ordenada por longitud de sufijo (el más largo gana; aquí sí cubren varias etiquetas) y ruta default opcional. Todas las búsquedas son insensibles a mayúsculas.

Estrategias de balanceo

EstrategiaAlgoritmo
round_robinSiguiente servidor sano en orden
weightedSmooth weighted round robin (nginx): con pesos 3:1 reparte 75/25 sin ráfagas largas
least_connMenos peticiones activas en este worker; si empatan, rotación
least_loadCarga de X-Backend-Load suavizada con EMA (α = 0,3), que caduca a los 5 s. Se eligen dos candidatos al azar (power of two choices) y gana el de menor carga. Si no hay carga fresca, decide least_conn; si también empatan, gana el que no tiene carga conocida (exploración)

Salud

  • Pasiva (hilo del loop): connect rechazado o reset antes de la respuesta cuentan como fallo; tras fall fallos seguidos, el servidor pasa a down. Sin sondas activas, pasado interval se reintenta en modo half-open: basta un fallo para volver a down.
  • Activa (hilo propio por generación): TCP connect o GET path esperando 2xx, cada interval; tras rise éxitos, up.
  • El estado (up, fails, oks) es atómico: es lo único que comparten los dos hilos.

Configuración y recarga en caliente

  1. Disparo: inotify sobre el directorio (cubre la escritura in situ y el rename de vim/sed -i), EVFILT_VNODE sobre fichero y directorio en kqueue, o SIGHUP. Debounce de 200 ms. Si el contenido no cambió, no se hace nada (salvo con SIGHUP).
  2. Validación en el master: TOML, reglas de coherencia y carga de certificados. Si falla, se registra el error y se mantiene la configuración actual.
  3. Envío del texto a cada worker, que construye la nueva generación, sincroniza sus listeners y cambia el puntero.
  4. Las peticiones en vuelo terminan con su generación; en las conexiones keep-alive, la petición siguiente ya usa la nueva.

La validación es estricta: una clave desconocida (workerz) es un error. Así una errata no se ignora en silencio.

Observabilidad

Log

Cada proceso tiene un ring buffer MPSC sin locks (cola acotada de Vyukov, 4096 × 512 B). El event loop y el hilo de health escriben en él, y un hilo consumidor vuelca bloques de hasta 64 KB con write() en O_APPEND, que no parte las líneas entre procesos. Si el ring se llena, el mensaje se descarta y se incrementa log_dropped: el loop nunca se bloquea.

Estadísticas

El master crea una región mmap(MAP_SHARED) antes del fork. Cada worker incrementa sus contadores atómicos (relaxed, cada uno en su línea de caché) y cada 250 ms publica su tabla de servidores con un seqlock. El master agrega todo y sirve JSON por el socket UNIX stats_socket. Un servidor aparece como degraded cuando los workers discrepan sobre su salud.

Limitaciones conocidas

  • El código kqueue (macOS/BSD) está implementado, pero solo se ha comprobado su sintaxis: falta ejecutarlo en un Mac.
  • Un cliente HTTP/1.0 recibe tal cual las respuestas chunked del backend.
  • Cambiar workers requiere reiniciar.
  • En una recarga, cada worker lee los certificados del disco en el hilo del loop (milisegundos, y solo al recargar).
  • El timeout upstream_connect no tiene test automático: en loopback un connect rechazado falla al instante.
