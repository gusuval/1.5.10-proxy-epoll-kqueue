Qué es y qué hace

El proxy se sitúa delante de tus servidores web. Escucha en uno o varios puertos (HTTP o HTTPS), mira el dominio que pide cada cliente y reenvía la petición a uno de los servidores del grupo configurado para ese dominio.

  • Varios puertos de entrada (frontends), cada uno con sus propias reglas.
  • Enrutamiento por dominio: exacto (api.test), comodín (*.example.com) y ruta por defecto.
  • HTTPS con varios certificados por puerto, elegidos por el nombre que pide el cliente (SNI).
  • Balanceo: round robin, por pesos, por menos conexiones o según la carga que informa cada servidor.
  • Tolerancia a fallos: detecta servidores caídos y los saca del reparto.
  • Recarga sin cortes: basta con guardar el fichero de configuración.
  • HTTP/1.1 completo: conexiones persistentes, pipelining, subidas grandes y WebSocket.

Plataformas: Linux (verificado). macOS y BSD están soportados en el código, pero aún no se han probado en esas plataformas. Windows no está soportado.

Compilar

meson setup build
meson compile -C build
meson test -C build --suite unit     # opcional: 5 suites de tests

Se generan tres programas: build/src/proxy (el proxy), build/tools/test_backend (servidor de pruebas) y build/tools/ws_probe (cliente WebSocket de pruebas). Para producción, compila en modo release:

meson setup build-release -Dbuildtype=release -Db_lto=true
meson compile -C build-release
sudo meson install -C build-release   # instala 'proxy' en /usr/local/bin

Primeros pasos (demo en 5 minutos)

El proyecto trae un generador de configuración de prueba con su propia autoridad certificadora.

# 1. Configuración + certificados de prueba en ./demo
./tests/gen_config.sh demo

# 2. Unos servidores de ejemplo
./build/tools/test_backend --port 19001 --name api-1 &
./build/tools/test_backend --port 19002 --name api-2 &
./build/tools/test_backend --port 19004 --name web-1 &

# 3. El proxy
./build/src/proxy -c demo/proxy.toml

En otra terminal:

curl -H 'Host: api.test' http://127.0.0.1:18080/
hello from api-1 path=/                  (+ una línea de relleno hasta 100 B)
curl -H 'Host: api.test' http://127.0.0.1:18080/
hello from api-2 path=/                  (round robin)
curl -H 'Host: www.example.com' http://127.0.0.1:18080/
hello from web-1 path=/                  (comodín *.example.com)

# HTTPS, verificando el certificado con la CA de la demo
curl --cacert demo/certs/ca.pem --resolve api.test:18443:127.0.0.1 https://api.test:18443/

Sin tocar /etc/hosts. curl --resolve o -H 'Host: …' bastan para probar dominios. Si quieres usar los nombres en el navegador: sudo ./tests/hosts.sh add (se deshace con remove).

Para parar: Ctrl+C en la terminal del proxy. Hace una parada ordenada.

Línea de comandos y señales

proxy -c <config.toml> [-t] [-w N]
  -c  fichero de configuración TOML (obligatorio)
  -t  solo valida la configuración y sale
  -w  fuerza el número de workers

Valida siempre antes de desplegar:

$ ./build/src/proxy -t -c demo/proxy.toml
configuración OK: 3 frontends, 8 backends, 2 workers

El proxy arranca un proceso master y N procesos worker. Las señales van siempre al master:

SeñalEfecto
SIGHUPRecarga la configuración (también se recarga sola al guardar el fichero)
SIGTERM, SIGINTParada ordenada: deja de aceptar conexiones y espera hasta 10 s a las peticiones en curso
kill -HUP $(pgrep -o -f 'proxy -c')      # -o: el más antiguo = master

Si un worker muere, el master lo relanza automáticamente.

Enrutamiento por dominio

Para cada petición se toma el dominio de la cabecera Host (sin puerto, sin distinguir mayúsculas) y se busca en las rutas del frontend por el que entró, en este orden:

  1. Dominio exacto: api.test.
  2. Comodín: *.example.com cubre a.example.com y a.b.example.com, pero no example.com. Si varios encajan, gana el más específico (*.eu.example.com antes que *.example.com).
  3. default, si existe.
  4. Si nada encaja: 404.
Host pedidoRutas: api.test · *.example.com · default
api.test, API.TEST:8080api.test
www.example.com*.example.com
example.com, otro.testdefault (sin default: 404)

Cada petición de una conexión persistente se enruta por separado. El backend recibe además X-Forwarded-For, X-Forwarded-Proto (http/https) y X-Real-IP con la IP del cliente.

HTTPS y certificados

Un frontend con tls = true termina HTTPS (TLS 1.2 y 1.3); hacia los backends el tráfico va en HTTP normal. Puedes poner varios certificados en el mismo puerto: se elige según el nombre (SNI) que envía el cliente.

[[frontend]]
name   = "web-tls"
listen = "0.0.0.0:443"
tls    = true
certs  = [
  { sni = "api.test",      cert = "certs/api.crt",  key = "certs/api.key" },
  { sni = "*.example.com", cert = "certs/wild.crt", key = "certs/wild.key" },
]
default_cert = 0
  • cert: certificado en PEM; puede incluir la cadena intermedia a continuación.
  • key: clave privada en PEM, sin contraseña. Se comprueba que corresponde al certificado.
  • En sni, el comodín cubre una sola etiqueta (*.example.com no vale para a.b.example.com), igual que en los certificados reales.

Si el cliente pide por SNI un nombre y luego envía un Host distinto que su certificado no cubre, recibe 421 Misdirected Request.

Crear un certificado de prueba

openssl req -x509 -newkey rsa:2048 -nodes -days 365 -sha256 \
  -keyout certs/api.key -out certs/api.crt \
  -subj "/CN=api.test" -addext "subjectAltName=DNS:api.test"

Comprobar qué certificado sirve el proxy:

openssl s_client -connect 127.0.0.1:443 -servername api.test </dev/null 2>/dev/null \
  | openssl x509 -noout -subject

Balanceo de carga

EstrategiaCómo reparteÚsala cuando…
round_robinPor turnosLos servidores son iguales y las peticiones parecidas
weightedProporcional a weight, sin ráfagasHay máquinas de distinta capacidad
least_connAl que tiene menos peticiones en cursoAlgunas peticiones son mucho más lentas que otras
least_loadAl que informa de menos cargaLos servidores pueden medir su propia carga

Cómo informa un servidor de su carga

Con least_load, cada servidor añade a sus respuestas la cabecera X-Backend-Load con un número de 0.0 (libre) a 1.0 (saturado). El proxy la lee, la suaviza para evitar saltos bruscos y la elimina antes de responder al cliente.

HTTP/1.1 200 OK
Content-Type: application/json
X-Backend-Load: 0.37

Si un servidor deja de enviarla durante más de 5 s, su carga se considera desconocida y se reparte por conexiones activas.

El reparto es por worker: con 8 workers, cada uno aplica la estrategia a sus propias peticiones, y el efecto global es el mismo.

Health checks

  • Pasivos (siempre activos): si conectar a un servidor falla fall veces seguidas, deja de recibir tráfico. Sin sondas configuradas, se vuelve a probar pasado interval.
  • Activos (sección [backend.health]): el proxy consulta cada servidor cada interval ms, por TCP o con GET path esperando 2xx. Tras fall fallos pasa a "down"; tras rise éxitos vuelve a "up".

Cuando un servidor falla al conectar, la petición se reintenta en otro sin que el cliente lo note. Si no queda ninguno sano, el cliente recibe 503. Los cambios de estado quedan en el log:

[warn] [w0] backend 'api' servidor 127.0.0.1:9002 -> DOWN (sonda http)
[warn] [w0] backend 'api' servidor 127.0.0.1:9002 -> UP (sonda http)

Recarga en caliente

Para cambiar la configuración, edita y guarda el fichero: el proxy lo detecta en menos de un segundo (funciona igual con editores que guardan por renombrado, como vim, o con sed -i). También puedes forzarla con kill -HUP.

  • La nueva configuración se valida entera antes de aplicarse. Si tiene un error, se descarta, se mantiene la actual y el motivo queda en el log.
  • Las peticiones en curso terminan con la configuración anterior; las nuevas usan la nueva. No se corta ninguna conexión.
  • Se pueden añadir o quitar frontends (puertos), rutas, backends, servidores y certificados.
  • Cambiar workers o stats_socket requiere reiniciar.
[info]  [master] configuración recargada (cambio en fichero)
[error] [master] recarga rechazada, se mantiene la configuración actual:
                 TOML inválido: line 133: syntax error

Logs

Formato: fecha [nivel] [proceso] mensaje. El proceso es master o wN. Cada petición genera una línea de acceso:

2026-09-26T23:12:47.184Z [access] [w0] 127.0.0.1 api.test "GET /hola" 200 127.0.0.1:19001 1ms
                                        │         │         │           │   │               └ latencia
                                        │         │         │           │   └ servidor que respondió
                                        │         │         │           └ código HTTP
                                        │         │         └ método y ruta
                                        │         └ dominio (Host)
                                        └ IP del cliente

Con mucho tráfico, desactiva el access log (access_log = false) o usa log_level = "warn".

             [--threads N] [--bind IP] [--drop-every N]

/ (cualquier otra)hello from NOMBRE path=… más relleno hasta 100 B

--load 0.3 fija la cabecera X-Backend-Load; --load-auto la calcula según las conexiones activas.

Cliente WebSocket: ws_probe

ws_probe --host api.test 127.0.0.1 18080 /ws "hola"
ws_probe --tls --ca demo/certs/ca.pem --sni api.test 127.0.0.1 18443 /ws "hola"

Tests automáticos

meson test -C build --suite unit   # 31 tests unitarios
./tests/integration/run.sh         # 96 comprobaciones de extremo a extremo (~20 s)

El script de integración genera su propia configuración, lanza 12 servidores y el proxy, comprueba todas las funcionalidades y lo limpia todo al terminar. PORT_BASE=N cambia los puertos y KEEP_WORK=1 conserva los ficheros para inspeccionarlos.

Benchmark

./bench/bench_proxy.sh                           # 30 s por escenario
DURATION=10s WORKERS=4 ./bench/bench_proxy.sh    # variante rápida

El script compila en release, reparte CPUs entre wrk, el proxy y los backends, y deja un informe en bench/results/. Resultado de referencia (8 workers, WSL2, Ryzen 7 7735HS): 223.705 req/s por HTTPS con 100 conexiones y 337.904 por HTTP, sin errores.
